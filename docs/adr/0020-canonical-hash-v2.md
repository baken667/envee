# ADR-020: Канонический хеш конфига v2 и миграция хранилища доверия

- **Статус**: Accepted
- **Дата**: 2026-09-09
- **Заменяет**: часть ADR-0004 (способ вычисления `sha256(canonical content)`)
- **Решает**: Что именно хешируется при одобрении конфига и что происходит с уже выданными одобрениями

## Контекст

ADR-0004 закрепил доверие через `sha256` канонического содержимого: одобрение
привязано к смыслу файла, а не к его байтам, поэтому правка комментария или
стиля кавычек не требует повторного `envee trust`. В Go-версии «канонический
вид» был побочным продуктом библиотеки: файл разбирался `BurntSushi/toml`,
а затем **сериализовался ею обратно**, и хешировался результат. Формат
этого результата нигде не был описан — он определялся текущей версией
библиотеки, порядком полей в её энкодере и его отступами.

При переписывании на Zig (ADR-0019) воспроизвести этот вывод побайтно без
самой библиотеки невозможно и не нужно: он никогда не был спецификацией.

## Решение

### Формат v2

Каноническое представление — **плоский отсортированный список строк**, по
одной на каждое листовое значение:

```
"env"."DEBUG" = true
"env"."PORT" = 5432
"env"."_"."path" = ["./bin", "{{config_root}}/node_modules/.bin"]
"profiles"."dev"."env"."LOG_LEVEL" = "debug"
"servers"[0]."host" = "a"
"servers"[1]."host" = "b"
"tools" = {}
```

Правила (реализация — `writeCanonical` в `src/toml/value.zig`):

- Путь к значению — цепочка ключей, каждый ключ **в кавычках JSON**, через
  точку. Без кавычек ключ `a.b` и путь `a` → `b` дали бы одинаковый текст,
  и подмена одного другим не меняла бы хеш.
- Строки — в кавычках JSON; целые и дробные числа и логические значения —
  в своём текстовом виде; массивы скаляров — в квадратных скобках через
  `, `; массив таблиц разворачивается по индексам (`"k"[0]."f"`).
- Пустая таблица оставляет строку `"k" = {}`: иначе `[a]` без содержимого и
  полное отсутствие `a` дали бы один хеш.
- Строки сортируются байтово по всему тексту строки, каждая завершается
  `\n`.
- Хеш — `sha256` от этого текста, записывается как `sha256:<hex>`.

Это **не TOML** и не предназначено для чтения обратно; это вход хеш-функции.
Инвариант, ради которого он существует, зафиксирован тестами в
`src/toml/value.zig`: форматирование, комментарии, стиль кавычек, порядок
ключей и CRLF хеш не меняют, а любое смысловое отличие — меняет.

### Версия записи доверия

Записи хранилища получают поле `version: 2`. Записи с `version: 1`
(выданные Go-версией) читаются, но считаются **неизвестными**: их хеш
заведомо не совпадёт с v2, и притворяться, что файл одобрен, нельзя.
Запреты (`deny`) хранятся под хешом пути и версии не имеют — они действуют
как раньше.

На практике переход означает **один повторный `envee trust` на каждый
проект**. `envee status` и `envee doctor` показывают такие проекты как
неодобренные с обычной подсказкой.

Остальные поля записи, их порядок и представление времени сохранены как в
Go (`expires_at` всегда присутствует, бессрочная запись несёт нулевое время
`0001-01-01T00:00:00Z`), поэтому файлы обеих реализаций взаимно читаются, а
подпись ed25519 (ADR-0004) считается по тем же байтам: подпись Go-версии
проверяется Zig-версией и наоборот.

## Альтернативы

- **Воспроизвести энкодер BurntSushi.** Отвергнуто: это привязка к
  внутренностям чужой библиотеки конкретной версии, и любое её обновление в
  прошлом уже могло молча менять хеши.
- **Хешировать сырые байты файла.** Отвергнуто: противоречит ADR-0004 —
  каждая правка комментария требовала бы повторного одобрения.
- **Мигрировать записи автоматически** (перечитать файл, пересчитать хеш,
  переписать запись). Отвергнуто: запись v1 удостоверяет содержимое, которое
  человек видел тогда; пересчитать хеш по файлу сейчас — значит одобрить
  текущее содержимое без просмотра.

## Последствия

### Положительные

- Формат описан и проверяем; хеш не зависит от библиотек.
- Подмена структуры ключей (`a.b` против `a` → `b`) меняет хеш.

### Отрицательные

- Одноразовый повторный `envee trust` для каждого проекта при обновлении с
  0.3.x.

### Нейтральные

- Инструменты, читающие хранилище (CI, скрипты), должны ожидать поле
  `version` и трактовать `1` как устаревшее.

## Заметки для будущих ревизий

Любое изменение правил канонического вида — это `version: 3` и новый ADR,
даже если меняется только сортировка.
